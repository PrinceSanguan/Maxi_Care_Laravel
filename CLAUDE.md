## Project overview

"Maxi-Care" / "Maxi Health Inventory Management System" — a Laravel 10 (PHP ^8.1, MySQL) pharmacy inventory + sales app. Two roles share one app: **admin** manages staff accounts and views sales reports; **staff** runs day‑to‑day inventory (receiving, sales, stock, suppliers, categories, products, expired items).

The README.md is the stock Laravel placeholder — ignore it.

## Common commands

```bash
composer install
cp .env.example .env && php artisan key:generate    # first-time setup
php artisan migrate                                  # creates tables AND seeds default admin + sample medicines (data is seeded inside migrations, NOT via DatabaseSeeder)
php artisan serve                                    # http://localhost:8000
php artisan migrate:fresh                            # full reset; re-runs the inline seed data in the migration files

# Tests (stock Laravel scaffolding only — there is no real suite yet)
php artisan test                                     # or: vendor/bin/phpunit
vendor/bin/phpunit --filter=ExampleTest              # single test

# Code style (Pint is installed but not wired into CI)
vendor/bin/pint
```

Default admin credentials are inserted by `database/migrations/2014_10_12_000000_create_users_table.php` (email `admin@gmail.com`, plus a pre-hashed password literal in the migration). Create staff accounts from the admin dashboard.

**Vite / npm are NOT part of the normal dev loop.** Blade views load per-page CSS straight from `public/css/*.css` via `asset()`, plus Bootstrap 5 / FontAwesome / DataTables from CDNs. `vite.config.js` and `package.json` are leftover scaffolding — don't add new styles to `resources/css` expecting them to be bundled.

## Architecture

### Role-based routing (no resource controllers, no `auth` group)

All routes live in a flat `routes/web.php` and are organised by URL prefix (`admin/...`, `staff/...`). Access control happens **inside each controller's constructor** by attaching a middleware alias:

- `AdminController::__construct` → `$this->middleware('checkAdminRole')`
- `StaffController::__construct` → `$this->middleware('checkStaffRole')`

Aliases are registered in `app/Http/Kernel.php` (`$middlewareAliases`) and point at `App\Http\Middleware\CheckAdminRole` / `CheckStaffRole`. Both check `Auth::user()->userRole` against a string (`'admin'` or `'staff'`) and redirect to `login` on mismatch — there is no `auth` middleware in front; the role check itself doubles as the auth gate.

`LoginController@loginForm` is the only entry point; after `Auth::attempt` it branches on `userRole` and redirects to either `admin.home` or `staff.home`. `/logout` is a closure that does `Session::flush(); Auth::logout();`. There is no separate registration — `SignupController` exists but is unrouted.

When adding a new role-protected page: add the route, then put the controller method on the matching `Admin`/`Staff` controller so it inherits the role middleware from the constructor. Don't try to compose role middleware in the route definition.

### Inventory data flow (this is the part that's easy to break)

Four tables move in lockstep, joined by a generated `reference` string:

- `medicines` — catalogue (productName, category, price, prescription)
- `suppliers` — vendor directory
- `receives` — each delivery batch (supplier, product, quantity, `dateReceived`, `expired`, `safetyStock`/`stockAvailable` split, `reference`)
- `stocks` — running balance per `reference` (`stockIn`, `stockOut`, `stockAvailable`, `safetyStock`, `expired`)
- `sales` — point-of-sale rows (reference, productName, quantity, price, amount)

Rules enforced by `StaffController` (not by DB constraints — so changes here must preserve them):

1. **`reference` is generated by `StaffController::generateReferenceNumber()`** as `MMDDYYYY` + 3-digit zero-padded sequence for that day, derived from the highest existing `receives.reference` for today. Both `receives` and `stocks` rows share the same reference, and that's how `updateReceive` / `expiredList` look them up. Don't introduce code paths that create one without the other.
2. **`receiveForm`** writes to `receives` AND creates a paired `stocks` row in the same request. The `stockType` form field routes the quantity into either `safetyStock` or `stockAvailable` — only one is non-zero per batch. `productCategory` and `amount` on the receive row are derived from the matching `medicines` row, not from the form.
3. **`newSales`** runs inside a `DB::beginTransaction()` and must rollback if the matched `stocks.stockAvailable < quantity` or if no `stocks` row matches `productName`. Price comes from `Receive`, not `Medicine`. It increments `stockOut` and decrements `stockAvailable` on the stock row. Any new sale-affecting logic must preserve the transaction boundary.
4. **`expiredList`** is a read endpoint with side effects: every `Receive` with `expired <= now` has its paired `Stock` rewritten so `stockAvailable` is moved into the `expired` column and zeroed out. Don't convert this to a "view only" page without moving the bookkeeping elsewhere.

Models use mass assignment (`$fillable`) but no relationships are declared — joins happen by looking up `productName` / `reference` strings in the controller. Treat those columns as effective foreign keys.

### Views

Blade templates live in `resources/views/{admin,staff}/`. Each page is a self-contained HTML document that `@include`s `{admin,staff}/sidebar.blade.php`; there is no shared root layout. Per-page CSS files in `public/css/` are named to match the view (`sales.blade.php` ↔ `public/css/sales.css`).

### Deployment quirk

The root-level `index.php` is **not** the Laravel public entrypoint — it's a shared-hosting wrapper that references `__DIR__.'/laravel/...'`, i.e. it expects this whole project to be deployed inside a `laravel/` subdirectory of the web root. For local work always use `php artisan serve` (which uses `public/index.php`). Don't "fix" the root `index.php` to match local paths unless you're intentionally changing the deployment model.
